# Demand 上界语义修正（`compromise` 判空 + 消费者取含端点上限）

日期：2026-09-30 11:11
涉及：`src/demand_.rs`、`src/slice_impl_.rs`、`src/buffer/segm_.rs`、`src/pipelining/join.rs`、
`tests/segm_async_io.rs`

> ⚠️ **本文的「决策」部分已被后续的 `Demand` 表示法重设计取代**，见
> [demand-20260930-2154.md](demand-20260930-2154.md)：新设计把「含端点上限」直接做进了
> `Demand` 语义（`NoMoreThan` 含端点、`max()` 即最大取值、`BaseAndLen` 用起点 + 长度），
> 上一轮为绕开 off-by-one 而加的 `max_count_`、`less_than(size + 1)`、`max - 1` 补丁已随
> 重设计删除。本文保留的价值是**两个缺陷的发现过程与证据**（`compromise` 判空会 panic、
> 消费者把开区间上界当含端点上限），以及对「只改一边会引入新 off-by-one」的推演。

## 1. 起因

为 `buffer::segm` 的四个「与 `TrInput` / `TrOutput` 交换数据」的异步实现补测试时，
发现两个独立缺陷（详见对话记录，此处只留因果链）：

1. **消费者侧读错语义**：`Demand` 的取值集是左闭右开区间 `[min, max)`，`max()` 是
   **开区间上界**；但搬移/读写实现把 `max()` 当成"含端点的最大数量"用
   （`if c >= max { stop }` + `take = min(remaining, max - c)`），于是可以搬 `max` 个。
   后果：`less_than(3)` 实搬 3（值集只允许 0..=2）、`exactly(n)` 在可搬量充足时搬 n+1。
2. **`Demand::compromise` 判空写松**：`AtLeast+LessThan`、`AtLeast+Range`、
   `LessThan+Range`、`Range+AtLeast` 四组 guard 用了非严格的 `<=`，两区间**恰好相接**
   （交集为空）时会走到 `Demand::between(x, x)` 而 panic；而 `Range+Range` 分支用严格的
   `b <= c` 判空是对的——既有测试的"不相交"用例恰好都绕开了会 panic 的分支。

判定"责任在谁"的依据（`Demand` 的模型自洽，是消费者读错）：

* `DemandRange::Range` 文档即 `[a, b)`，枚举头注释 "left-closed right-open"；
* `RangeBounds::end_bound` 对 `LessThan`/`Range` 返回 `Bound::Excluded`；
* `len()` 数的是半开区间的元素个数：`exactly(1)` → `min=1, max=2, len=1`；
* 既有测试 `try_from_usize_range(5..10)` → `(min 5, max 10)`。

因此"允许的最大数量"= `max - 1`。

## 2. 决策

### 2.1 `compromise`：保持 `[min, max)`，判空改严格，不 panic

四处 guard 由 `<=` 改为 `<`（`a < b`、`a < d`、`c < b`），并删掉 `Range+Range` 分支里
冗余的 `lower <= upper` 检查（由 `b > c`、`d > a` 可推出 `max(a, c) < min(b, d)`）。
契约明确为"返回交集；无交集（含恰好相接）返回 `None`"。

### 2.2 消费者：统一经 `demand_::max_count_` 取"含端点上限"

新增 `pub(crate) fn max_count_(&Demand<usize>) -> usize`：`max().map(|u| u - 1)`，
无上界取 `usize::MAX`（饱和表示）。**必须"先分辨无上界、再减一"**，否则无上界会被降一格。
四个异步实现（两个单步 + 两个 provided method）、两处 `take_segm_*`、`with_limit`、
6 处 `try_read/try_write`、`pipelining/join.rs` 全部改用它。

### 2.3 生产者侧："有 size 个可供搬移"必须写成 `less_than(size + 1)`

这是与 2.2 **成对**的改动，漏掉就会引入新的 off-by-one：旧写法 `less_than(size)` 在开区间
语义下表示"最多 size - 1 个"，于是修严消费者后 `exactly(size)` 与"恰好 size 个可用"取交集
会得到空集（永远少搬一个）。所有 `available` / `child_demand` / `needed_demand` 均改为
`size.saturating_add(1)` 形式。

配套：provided method 里新增"无错误且未搬动任何数据 ⇒ 退出"的防御分支，避免需求与可搬量
无交集时反复空转（当前构造下不可达，属兜底）。

### 2.4 不改的部分

* `range_` 的 `min` 缺省仍取 1（"一个都没搬 + 终止性错误"把错误抛给调用方，属有意策略，
  已加注释说明与取值集语义无关）；
* `less_than(0)` 仍作为"空需求"的表示（`max_count_` 得 0，消费者搬 0）。

## 3. 未决：`exactly(usize::MAX)` 的上界无法表示

`exactly(MAX)` 表示 `{MAX}`，其**开区间上界** `MAX + 1` 装不进 `usize`；当前实现退化为
`at_least(MAX)`，于是 `len()` 在该点饱和为 0（把 `{MAX}` 说成空集）、`max()` 返回 `None`
（把有上界说成无上界）。`max_count_` 在该点返回 `MAX`，恰好是 `{MAX}` 的正确上限，所以
"最多能搬多少"不受影响；受影响的只有 `len()`/`max()` 这两个极端查询（已文档化 + 测试固定）。

可选路线：

* **A（内部改为含端点上界 `Option<T>`，None = 无上界）**：构造时把开区间上界 `u` 存成
  `u - 1`。`exactly(n)` 变成 `(n, n)`，不再需要 `val < T::MAX` 特判；`at_least(l)` 的
  上界是真 `None`（不再借用 `MAX`）；`RangeBounds::end_bound` 用
  `upper.checked_add(1).map(Excluded).unwrap_or(Included(upper))` 才能覆盖 `MAX` 点；
  无上界时 `len()` 仍只能饱和。需要显式的空集分支处理 `less_than(0)`。
* **B（三态上界 `enum Upper<T> { Unbounded, Excluded(T), Included(T) }`）**：语义最直白
  （等价于 `core::ops::Bound`），代价是匹配臂与样板更多。
* **C（保持现状 + 文档化退化）**：本次采用的方案；`max_count_` 的答案在极端点依然正确。
  若要把 `len()`/`max()` 也做到精确，则需走 A 或 B，并把 `max_count_` 提升为公开 API。

顺带建议（公开 API 变更，需单独确认）：

* `Demand::max_count()`：消费侧唯一入口，省得每个调用点自己减一；
* `Demand::at_most(n)`（含端点，"最多 n 个"）：现在只能写 `less_than(n + 1)`，是新的易错点，
  本次在 `tests/segm_async_io.rs` 与 `pipelining/join.rs` 都踩到过。

## 4. 影响面与验证

* 行为变更：`less_than(n)` 类需求实际搬移量由 n 降为 n - 1；`exactly(n)` 由"可能 n + 1 /
  恰好 n 个可用时 panic"变为"恰好 n"。
* 下游：`buffex` 的 `ring` 段实现与 `abs_buff_tokio_adapt` / `abs_buff_compio_adapt` 以 git
  依赖引用 `abs_buff`，升级后需复核它们对需求的期望（尤其"最多 n 个"的写法）。
* 验证：`cargo test` 28（lib）+ 7（集成）+ 6（文档）；`cargo clippy --all-targets` 无告警。
  另做了三组变异校验：`compromise` guard 退回非严格 → Demand 测试失败；`max_count_` 多算
  一格 → 6/7 集成测试失败；生产者侧退回 `less_than(size)` → 含"恰好相等"回归在内的 3 个
  集成测试失败。所有变异均已按字节还原。
